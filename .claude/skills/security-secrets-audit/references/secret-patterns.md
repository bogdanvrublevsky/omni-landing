# Паттерны секретов и разбор инцидента

## Что ловит `scan-secrets.sh`

- PEM-заголовки приватных ключей (`-----BEGIN ... PRIVATE KEY-----`).
- AWS access key ID (`AKIA[0-9A-Z]{16}`).
- Telegram bot token (`\d{8,10}:[A-Za-z0-9_-]{30,45}`) — актуально для Cloudflare Worker → Telegram интеграции (`docs/adr/0005-cloudflare-workers-lead-gen.md`).
- Присвоения вида `password/secret/token/api_key = "значение"` (JSON/JS/YAML-стиль, значение в кавычках, ≥6 символов).
- Файлы с именами, характерными для секретов: `.env*`, `.dev.vars*`, `credentials*.json`, `*.pem`, `*.p12` — блокируются по самому факту коммита, независимо от содержимого.

## Что НЕ ловит (осознанные ограничения)

- Секреты без кавычек в неструктурированном тексте (например, вставленные в комментарий как есть) — низкая точность паттерна для такого случая, риск ложных срабатываний выше пользы.
- Секреты, закодированные (base64, hex) без узнаваемого префикса.
- Секреты, уже попавшие в git-историю до появления этого hook'а — сканирует только рабочее дерево/staged-файлы, не всю историю (для этого — отдельный проход `--all` плюс, при необходимости, `git log -p | grep`, вручную).

## Разбор реального инцидента (см. `.claude/memory/security.md`)

`ttapp/data/users.json` содержал `"password": "admin1234"` в открытом виде, закоммиченный в публичный репозиторий до появления этого скрипта. Если бы hook уже существовал на момент того коммита, паттерн `(password|...)['\"]?[[:space:]]*[:=][[:space:]]*['\"][^'\"[:space:]]{6,}['\"]` поймал бы его — это ровно тот случай, под который паттерн откалиброван (проверено тестом при разработке скрипта).

Урок: секрет остаётся в истории git даже после исправления HEAD (коммит `29e32e3`). Полная зачистка истории — отдельное, деструктивное действие (`git filter-repo`/BFG + force-push), выполняется только по явному запросу пользователя.

## Известный false positive

После ротации `ttapp/data/users.json` содержит `"password": "ROTATED_SET_VIA_ENV_BEFORE_USE"` — паттерн продолжает помечать это поле, потому что регулярка не отличает плейсхолдер от настоящего секрета (это и не должно быть её задачей — она про форму, не про семантику значения). Это осознанный компромисс: точечное исключение конкретной строки из паттерна сделало бы сканер менее надёжным как реальный инструмент безопасности. При ручном аудите такие срабатывания — ожидаемый шум, требующий взгляда человека, а не повод ослаблять паттерн.
