# Security Secrets Audit

## Назначение

Ручная, более глубокая проверка на утечку секретов, чем автоматический pre-commit hook — покрывает всю историю/рабочее дерево по запросу, а не только staged-файлы одного коммита. Мотивирован реальным инцидентом: в этом репозитории уже был закоммичен plaintext-пароль в публичную ветку (см. `.claude/memory/security.md`).

## Когда использовать

- Перед добавлением нового внешнего сервиса/интеграции (например, при реализации Cloudflare Worker → Telegram, см. `docs/adr/0005-cloudflare-workers-lead-gen.md`).
- Периодически, как deep-check всего репозитория, а не только последнего коммита.
- После любого инцидента или подозрения на утечку — как часть реагирования.

## Когда НЕ использовать

- Для рутинных изменений контента/копирайтинга без новых секретов — этого достаточно на уровне pre-commit hook (Stage 8), отдельный ручной аудит избыточен.
- Как замена pre-commit hook — hook обязателен всегда, этот skill дополняет его, не заменяет.

## Алгоритм

1. Запустить `scripts/run-audit.sh` из корня репозитория — сканирует **все** отслеживаемые файлы (`git ls-files`), не только staged.
2. Каждое срабатывание разобрать вручную: реальный секрет или false positive (см. `references/secret-patterns.md` — там задокументирован известный false positive в `ttapp/data/users.json`).
3. Если находится реальный секрет:
   - Немедленно заменить значение в HEAD на плейсхолдер/убрать (как было сделано в коммите `29e32e3`).
   - Проверить, публичный ли репозиторий (сейчас — да) — если да, считать секрет скомпрометированным и ротировать его в сервисе-источнике (не только в репозитории).
   - Задокументировать инцидент в `.claude/memory/security.md` (см. skill `memory-sync`).
   - Полную зачистку git-истории (`git filter-repo`/BFG + force-push) выполнять только по явному запросу пользователя — это деструктивная операция.
4. Проверить, что новый секрет (если он появляется легитимно — например, токен Cloudflare Worker) хранится через platform secret store (`wrangler secret`), а не в файле из репозитория, и что соответствующий файл (`.dev.vars` и т.п.) есть в `.gitignore`.

## Чеклист

- [ ] `scripts/run-audit.sh` запущен и вывод разобран полностью (не только первая строка).
- [ ] Каждое срабатывание классифицировано: реальный секрет / известный false positive / новый false positive (задокументировать в `references/secret-patterns.md`, если паттерн часто ложно срабатывает).
- [ ] Новые секреты интеграций — через secret store платформы, не через файл в репозитории.
- [ ] `.gitignore` покрывает файлы с локальными секретами для новой интеграции.

## Ошибки, которых стоит избегать

- Останавливаться после первого найденного секрета, не проверив весь вывод — `--all` может найти несколько независимых проблем разом.
- Ослаблять паттерны сканера ради конкретного false positive — снижает пользу инструмента для реальных будущих секретов (см. известный случай в `references/secret-patterns.md`).
- Ротировать секрет только в репозитории, не в самом сервисе — если репозиторий публичный, старое значение уже скомпрометировано независимо от того, что сейчас в HEAD.

## Лучшие практики

- Аудит — до пуша, не после. Публичный репозиторий делает откат постфактум частичным (история остаётся).
- Каждая новая внешняя интеграция — повод прогнать аудит заново, не только при подозрении на проблему.
