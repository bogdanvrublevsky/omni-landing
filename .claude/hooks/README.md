# Hooks — anltx (main/)

Все хуки настроены в `.claude/settings.json`, скрипты — в `.claude/hooks/scripts/`. Каждый хук протестирован вживую в реальной сессии Claude Code (не только unit-тестом скрипта отдельно) — см. "Ошибки" по каждому, где перечислены баги, найденные именно на этом этапе.

## session-start (SessionStart)

**Назначение:** напомнить Claude границы скоупа в начале каждой сессии, не полагаясь на то, что модель перечитает `CLAUDE.md` целиком.

**Условия запуска:** старт новой сессии Claude Code в этом репозитории.

**Действия:** печатает `additionalContext` с кратким напоминанием о скоупе (`main/` в фокусе, `dlext/ttapp/sgame/treev` — нет) и о правиле `<head>`.

**Ошибки:** нет (простой статический вывод, JSON-валидность проверена).

**Ограничения:** не может быть протестирован end-to-end в рамках одной сессии (требует реального рестарта Claude Code) — проверена только валидность JSON-вывода скрипта напрямую.

## scope-guard (PreToolUse: Edit\|Write\|MultiEdit\|NotebookEdit)

**Назначение:** механически блокировать правки внутри `dlext/`, `ttapp/`, `sgame/`, `treev/` — принуждает Claude остановиться и спросить пользователя, вместо того чтобы полагаться на то, что модель сама вспомнит про Scope из `CLAUDE.md`.

**Условия запуска:** любой вызов Edit/Write/MultiEdit/NotebookEdit с `file_path`, содержащим один из сегментов `dlext`, `ttapp`, `sgame`, `treev`.

**Действия:** `exit 2` + сообщение в stderr со ссылкой на `docs/adr/0006-monorepo-scope-boundary.md`.

**Ошибки:** нет — сработал корректно с первого раза при живом тесте (правка `ttapp/app.js` заблокирована).

**Ограничения:** не перехватывает запись в эти пути через Bash (`echo > ttapp/...`, `cp ... ttapp/`) — покрывает только прямые файловые инструменты. Если понадобится закрыть и этот путь, потребуется отдельный Bash-паттерн-хук.

## head-guard (PreToolUse: Edit\|Write\|MultiEdit)

**Назначение:** механически блокировать автономные изменения `<head>` (meta/GTM/GA4/CSP) — по правилу `CLAUDE.md` → AI Workflow.

**Условия запуска:** Edit/MultiEdit, где позиция редактируемого фрагмента (`old_string`) попадает внутрь `<head>...</head>` в файле на диске; Write, где записываемый контент содержит блок `<head>...</head>`. Применяется только к `.html`/`.htm`/`.astro`.

**Действия:** `exit 2` + сообщение в stderr.

**Ошибки, найденные при живом тестировании (важно для будущих правок этого хука):**
1. Первая версия матчила `<head` прямо в тексте правки (`old_string`/`new_string`) — не сработала на реальной правке `<title>`, потому что фрагмент правки не содержит сам тег `<head`, только соседнюю строку. Исправлено на позиционную проверку: читаем файл с диска, находим границы `<head>...</head>`, проверяем, попадает ли позиция правки в этот диапазон.
2. При переписывании скрипта через Write-инструмент старая версия хука заблокировала запись **самой себя**, потому что исходный код скрипта (комментарии/regex-паттерны) буквально содержит подстроки `<head` и `</head>`. Исправлено: проверка теперь применяется только к файлам с расширением `.html/.htm/.astro`, а не к любому Write-вызову.
3. Автоформаттер/линтер редактора однажды переписал `new RegExp("<head[\\s>]", "i")` в `new RegExp("<head[\s>]", "i")` — JS молча роняет нераспознанный `\s` внутри обычной строки, из-за чего паттерн стал `<head[s>]` и переставал матчить `<head lang="ru">` (с атрибутами). Исправлено переходом на regex-литералы (`/<head[\s>]/i`) везде — они не подвержены этому классу ошибки.

**Ограничения:** если один и тот же `old_string`-фрагмент текстуально встречается в файле несколько раз, проверяется только первое вхождение (`indexOf`) — теоретически возможен пропуск, если редактируется НЕ первое вхождение одинакового текста внутри `<head>`. Признанный компромисс ради простоты.

## secrets-precommit (PreToolUse: Bash)

**Назначение:** не дать закоммитить секрет — переиспользует `.claude/hooks/scripts/scan-secrets.sh` (тот же скрипт, что и skill `security-secrets-audit`).

**Условия запуска:** команда Bash содержит `git commit`.

**Действия:** запускает `scan-secrets.sh`; при находке — `exit 2` + вывод скрипта в stderr, коммит не происходит.

**Ошибки, найденные при живом тестировании:**
1. Первый живой тест (`printf ... > file && git add file && git commit ...` одной Bash-командой) прошёл **без блокировки**, хотя секрет был в файле. Причина: `PreToolUse` срабатывает один раз до выполнения всей командной цепочки — на момент проверки `git add` из этой же цепочки ещё не выполнился, `git diff --cached` не видел ничего застейдженного. Исправлено: если команда содержит одновременно `git add` и `git commit`, скрипт переключается на `scan-secrets.sh --all` (сканирует все отслеживаемые файлы, не только индекс) как safety net. Для отдельного `git commit` (файлы застейджены более ранним, отдельным вызовом) используется быстрый staged-режим — этот путь тоже проверен вживую и корректно блокирует.

**Ограничения:** `--all`-режим шумнее (может отметить уже известные/принятые false positives, например плейсхолдер в `ttapp/data/users.json` — см. `.claude/skills/security-secrets-audit/references/secret-patterns.md`) — это осознанный компромисс безопасности в пользу полноты, а не точности.

## dangerous-command-guard (PreToolUse: Bash)

**Назначение:** механически закрыть пункты `CLAUDE.md` → Forbidden Practices, которые касаются деструктивных/трудно обратимых команд — не полагаться только на то, что модель "помнит" про них в длинной сессии.

**Условия запуска:** команда Bash матчит один из паттернов: `git push --force`/`-f`/`--force-with-lease`, `git reset --hard`, `git clean -f`, `--no-verify`, `git filter-repo`/`filter-branch`, `rm -rf`/`rm -fr`, `git branch -D`.

**Действия:** `exit 2` + сообщение в stderr, требующее остановиться и спросить пользователя явно в чате (хук не может сам отличить "подтверждено" от "не подтверждено" — поэтому блокирует всегда, решение о повторе — за диалогом с пользователем).

**Ошибки:** unit-тест на матрице из 10 команд прошёл верно с первого раза; живой тест `git reset --hard HEAD` подтвердил блокировку в реальном вызове. Но при коммите самих файлов этого хука (в этой же сессии) хук дважды заблокировал собственный `git commit`, потому что commit-сообщение **текстом** упоминало `--no-verify` и `rm -rf` как примеры — паттерн сканирует всю строку команды целиком, а не только реальные CLI-флаги, и не отличает "флаг в вызове" от "флаг, процитированный в тексте сообщения". Сообщение коммита пришлось переформулировать без буквальных вхождений guarded-паттернов.

**Ограничения:**
- Список паттернов заведомо неполный (например, не ловит прямой push в `main` в обход PR — это не определяется по одной команде без знания состояния веток/PR). Расширяется по мере необходимости, не претендует на исчерпывающий список всех деструктивных команд.
- Сканирует сырую строку команды целиком, включая содержимое кавычек/heredoc — команда, которая просто *упоминает* guarded-паттерн в тексте (например, в теле коммита), блокируется наравне с командой, которая его реально использует. Ложные срабатывания такого рода — известный и принятый компромисс (см. "Ошибки" выше).

---

## Общее ограничение всех PreToolUse-хуков

Хуки перехватывают только действия, совершаемые самим Claude Code через его инструменты (Edit/Write/Bash и т.д.) **внутри сессии**. Они не защищают от того, что пользователь делает вручную вне Claude Code (прямой `git commit` в терминале, правки в другом редакторе). Для такой защиты — секреты всё ещё проверяются в `security-secrets-audit` skill, который можно запускать вручную в любой момент.
