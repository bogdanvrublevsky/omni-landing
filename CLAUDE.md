## Project

**anltx** (домен anltx.xyz) — продающая контентная платформа для монетизации аналитической экспертности. Бизнес-модель: freemium. Бесплатный контент (блог, раздел полезностей) наращивает авторитет и трафик, который конвертируется в платные консультации и внедрение аналитики. Продаётся не информация (её можно найти бесплатно где угодно), а экспертность и опыт.

Целевая аудитория: начинающие веб-, дата-, системные аналитики и дата-инженеры.

## Goals

### Краткосрочные (MVP)
- Посадочная страница с информацией об экспертизе и услугах.
- Структура для блога и раздела полезностей (может быть пустой контентно на старте, но технически готовой).
- Двуязычность EN/RU с раздельными путями и переключением.
- Деплой на anltx.xyz через GitHub Pages, автодеплоем.
- Веб-аналитика (GTM + GA4) с cookie consent.
- Форма лидогенерации → уведомление в Telegram.
- Техническая SEO-база (sitemap, robots.txt, meta/OG, hreflang).

### Долгосрочные
- Наполнение блога и раздела полезностей реальным контентом.
- Собственная CMS (в рамках этого проекта, отдельная фаза — архитектура не определена, см. `docs/adr/0004-custom-cms-direction.md`).
- Переход с GitHub Pages на полноценный хостинг при появлении платящих клиентов.
- `lwtms`/`sstms`/`dlext` — отдельные продуктовые направления ("аналитическая платформа"), вне скоупа текущей инфраструктуры, см. `docs/roadmap.md`.

## Architecture

- **Тип:** статический сайт (SSG), без бэкенда, без серверного состояния.
- **Build:** Astro — компилируется в чистый HTML/CSS/JS, без клиентского рантайм-фреймворка.
- **Контент:** Astro Content Collections (Markdown + frontmatter) для блога и раздела полезностей; лендинг — Astro-компоненты/страницы напрямую.
- **i18n:** раздельные пути `/en/` и `/ru/` через встроенный Astro i18n routing. Автоопределение локали по `Accept-Language` при первом визите + ручной переключатель, выбор сохраняется в `localStorage`.
- **Хостинг (MVP):** GitHub Pages, кастомный домен `anltx.xyz` (уже настроен, DNS живой).
- **CI/CD:** GitHub Actions, автодеплой на push в `main`.
- **Лидогенерация:** клиентская форма → Cloudflare Worker (serverless) → Telegram Bot API.
- **Аналитика:** GTM-контейнер + GA4-свойство. Google Search Console уже верифицирован для домена.
- **Auth / серверное хранилище:** отсутствуют в MVP. Понадобятся, когда появится платная часть платформы (Beta/Production, см. roadmap) — тогда потребуется миграция с чисто статического хостинга.
- **CMS:** будущая фаза, архитектура не определена. Любые решения по структуре контента сейчас должны оставаться совместимыми с Content Collections как источником данных — это снижает риск при будущей миграции на CMS.

Подробности и обоснования — в `docs/adr/`.

## Stack

- Astro (SSG) + HTML5/CSS3 + минимальный vanilla JS (только там, где нужна интерактивность: переключатель локали, форма)
- Markdown + frontmatter (Content Collections)
- Node.js/npm — только на этапе сборки (CI), не в проде
- GitHub Actions — CI/CD
- GitHub Pages — хостинг (MVP-фаза)
- Cloudflare Workers — serverless-функция для формы
- GTM + GA4 — аналитика
- Telegram Bot API — уведомления о лидах

## Coding Rules

- Никаких TODO/FIXME/placeholder в закоммиченном коде — задача либо сделана, либо не сделана.
- Никакой преждевременной абстракции: компонент выделяется, когда дублирование уже возникло (не "на будущее").
- Клиентский JS — минимум. По умолчанию — статический HTML. JS только для локаль-свитчера и отправки формы.
- Контент публикуется только когда заполнен на обоих языках (см. Definition of Done).
- Не трогать `dlext/`, `ttapp/`, `sgame/`, `treev/` без явного отдельного запроса пользователя.

## Git Workflow

- Trunk-based без feature-веток и PR: вся работа коммитится и пушится напрямую в `main`. Feature-ветки не создаются и не используются.
- `main` всегда должен оставаться рабочим и задеплоенным — в него коммитится только то, что готово к проду.
- Lint и build обязаны пройти локально до пуша — это гейт перед пушем, а не часть ревью.

## Review Rules

- Lint обязан пройти до пуша — это гейт, а не отдельный этап ревью.
- Ревью выполняет владелец проекта вручную, глядя на diff перед тем как подтвердить пуш (формального PR-ревью нет, но проверка перед пушем — обязательна).
- Чек-лист ревью: контент на обоих языках, нет секретов, нет битых ссылок, соответствует Definition of Done.
- Код, написанный AI, ревьюится с той же строгостью, что и написанный человеком — исключений нет.

## Testing

- MVP-фаза: техническая проверка — сборка проходит, lint проходит (Astro check + HTML/CSS/JS), внутренние ссылки валидны, обе локали структурно присутствуют.
- Lighthouse как гейт перед пушем в `main`: Performance / Accessibility / Best Practices / SEO — цель ≥ 90 по каждой категории.
- SEO-контент-стратегия (тексты, семантика) — тестируется позже, отдельной фазой (осознанно отложено).
- E2E-тестов на MVP не требуется. Форма лидогенерации проверяется вручную при каждом изменении, затрагивающем её (build-time данные и логика меняются редко).

## Security

- Секреты (токены, пароли, ключи) никогда не коммитятся — гейт: pre-commit secrets-scan hook (см. `.claude/hooks/`).
- Токен Telegram-бота для Cloudflare Worker живёт только в Wrangler secrets, никогда в репозитории и никогда в `.dev.vars` (файл в `.gitignore`).
- Cookie consent banner обязателен и должен гейтить загрузку GTM/GA4 до согласия пользователя (GDPR/ePrivacy, двуязычная аудитория).
- `<head>` (meta-теги, GTM/GA4-сниппеты, CSP) никогда не изменяется Claude автономно — только по явному подтверждению пользователя.
- **Известный инцидент:** в `ttapp/data/users.json` был закоммичен plaintext-пароль администратора в публичный репозиторий. Ротирован в коммите `29e32e3` (main). Старое значение остаётся в истории git — принято как остаточный риск, т.к. `ttapp` вне текущего скоупа; полная зачистка истории (force-push) не выполнялась без отдельного явного запроса.

## AI Workflow

**Claude делает автономно, без запроса подтверждения:**
- Пишет и редактирует код: Astro-компоненты, layouts, конфиги, CI-workflow.
- Пишет некопирайтерский текст интерфейса на обоих языках (CTA, микрокопия, UI-лейблы, служебные тексты).

**Claude готовит черновик, но не публикует самостоятельно:**
- Тексты статей блога и раздела полезностей — это контентная/маркетинговая экспертиза автора, Claude может помогать с черновиком, но финальное решение и публикация — за пользователем.

**Категорически запрещено без явного подтверждения:**
- Стратегические или маркетинговые решения (позиционирование, цены, оффер).
- Деплой в прод — то есть push/merge в `main`.
- Изменение `<head>` (meta, GTM/GA4, CSP).
- Изменение DNS/домена.
- Любые изменения за пределами скоупа этого документа (`dlext/`, `ttapp/`, `sgame/`, `treev/`).

**Подтверждение обязательно перед:**
- Мержем в `main` и любым push в удалённый репозиторий.
- Изменением `.claude/settings.json` (permissions, hooks).
- Добавлением новых внешних зависимостей/сервисов (пример: новый serverless-провайдер, новая аналитика).

## Definition of Done

Страница/фича считается готовой, когда:
1. Контент заполнен на обоих языках (EN + RU).
2. Lint проходит.
3. Lighthouse проходит установленный порог (Testing).
4. Аналитика (GTM/GA4-события, если применимо) настроена и проверена.
5. Cookie consent корректно гейтит загрузку аналитики.
6. Задеплоено и доступно в проде на обоих языках.
7. Пройден ручной review владельцем проекта.

## Forbidden Practices

- Коммитить секреты/токены/пароли в любом виде.
- Push в `main` (или любой другой удалённый репозиторий) без явного подтверждения пользователя на этот конкретный пуш.
- Создавать и использовать feature-ветки — вся работа идёт напрямую в `main`.
- Менять `<head>`, DNS или конфигурацию GTM/GA4 без явного подтверждения.
- Трогать `dlext/`, `ttapp/`, `sgame/`, `treev/` без отдельного явного запроса.
- Оставлять TODO/FIXME/placeholder-контент в замердженном коде.
- Использовать `--no-verify` или иначе пропускать hooks.
- Переписывать git-историю / force-push без явного подтверждения.

## Decision Making Rules

- Масштабируемость и сопровождаемость важнее преждевременной оптимизации.
- Простота по умолчанию: статика-first, сложность (бэкенд, auth, динамическая инфраструктура) добавляется только под конкретное требование MVP/Beta, а не "про запас".
- Любое нетривиальное архитектурное решение оформляется ADR до реализации.
- Если решение неоднозначно или имеет реальные компромиссы — задать вопрос пользователю, а не выбирать молча за него. Молчаливые дефолты допустимы только для чистого стиля кода.
