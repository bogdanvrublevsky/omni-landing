# 0002 — i18n через раздельные пути /en/ и /ru/

- **Статус:** принято
- **Дата:** 2026-07-21

## Контекст

Сайт anltx двуязычный (EN/RU) с самого MVP. Нужна схема адресации локализованного контента и способ переключения между языками.

## Проблема

Нужно выбрать, как URL отражают язык страницы, и как определяется язык при первом визите — от этого зависят SEO (hreflang, индексация в Google Search Console, уже верифицированном для домена), кешируемость на CDN GitHub Pages и сложность реализации.

## Варианты

1. **Один HTML с JS-переключением контента "на лету".** Один URL на страницу независимо от языка — просто для навигации, но плохо для SEO (поисковик видит один документ, а не две проиндексированные версии), требует client-side логики для первого рендера контента.
2. **Поддомены (`en.anltx.xyz`, `ru.anltx.xyz`).** Чёткое разделение, но требует дополнительной DNS/CNAME настройки и усложняет деплой на GitHub Pages (Pages отдаёт один сайт с одним CNAME на репозиторий).
3. **Раздельные пути (`/en/...`, `/ru/...`).** Каждая локаль — самостоятельно индексируемый набор URL, совместим с hreflang и sitemap, не требует дополнительной DNS-конфигурации, поддерживается Astro "из коробки" через встроенный i18n-роутинг.

## Принятое решение

Раздельные пути `/en/` и `/ru/`. Автоопределение локали по `Accept-Language` при первом визите (редирект на нужный путь), плюс ручной переключатель в UI; выбор пользователя сохраняется в `localStorage` и имеет приоритет над автоопределением при повторных визитах.

## Последствия

- Требуется hreflang-разметка между парными EN/RU страницами (входит в техническую SEO-базу MVP, см. [analytics.md](../../.claude/memory/analytics.md)).
- Content Collections (см. ADR 0003) должны нести признак локали во frontmatter, чтобы Astro i18n-роутинг мог сопоставлять пары статей.
- Любое изменение структуры путей после запуска требует отдельного ADR — затрагивает уже верифицированный Google Search Console (см. `CLAUDE.md` → Refactoring Rules).
