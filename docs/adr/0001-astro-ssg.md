# 0001 — Astro как build-инструмент для сайта anltx

- **Статус:** принято
- **Дата:** 2026-07-21

## Контекст

Сайт anltx — двуязычный (EN/RU) лендинг + блог + раздел полезностей, деплоится на GitHub Pages как статика. Изначально предполагался безсерверный чистый HTML5/CSS/JS без build-шага.

## Проблема

При двух локалях и растущем числе страниц блога чистый HTML приводит к дублированию общей разметки (шапка, футер, меню) в каждом файле × 2 языка. Любое изменение навигации требует правки во всех копиях вручную, что создаёт риск рассинхрона между локалями и не масштабируется на объём блога.

## Варианты

1. **Чистый HTML/CSS/JS без build-шага.** Максимально просто и прозрачно, но дублирование шапки/футера/меню в каждом файле × 2 локали; риск рассинхрона растёт вместе с объёмом контента.
2. **Eleventy (11ty).** Лёгкий статический генератор, гибкий шаблонизатор, но i18n-роутинг нужно настраивать вручную — нет готового решения для раздельных путей `/en/`/`/ru/`.
3. **Astro.** Компилируется в чистый статический HTML/CSS/JS (без клиентского рантайма), даёт переиспользуемые компоненты, встроенный i18n-роутинг по путям, Content Collections для блога. Требует Node.js только на этапе сборки (CI), не в проде.
4. **Next.js / полноценный SPA-фреймворк.** Избыточен — рассчитан на SSR/динамику, которых у проекта нет; усложняет деплой на GitHub Pages.

## Принятое решение

Astro. Даёт переиспользуемые компоненты и встроенный i18n-роутинг именно под нужную схему (`/en/`, `/ru/`), при этом продолжает компилироваться в чистую статику, совместимую с текущим GitHub Pages деплоем — минимальное усложнение ради устранения конкретной, уже проявившейся проблемы дублирования.

## Последствия

- В CI (`GitHub Actions`) появляется build-шаг (`npm ci && npm run build`) — раньше деплой был прямым копированием файлов.
- `main/` перестаёт быть просто набором статических файлов и становится Node/npm-проектом (потребует `package.json`, лок-файл теперь коммитится — см. `.gitignore`).
- `deploy.yml` нужно будет переписать под сборку Astro вместо `cp -r main/* _site/` — отдельная задача при фактической миграции (не часть инфраструктурного бутстрапа), см. [deployment.md](../../.claude/memory/deployment.md).
- Требует минимальной кривой обучения (шаблонизация Astro) — разовые затраты, не на каждую страницу.
