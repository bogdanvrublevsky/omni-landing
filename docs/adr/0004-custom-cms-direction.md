# 0004 — Кастомная CMS: направление, не архитектурное решение

- **Статус:** принято (как декларация направления; конкретная архитектура ещё не выбрана)
- **Дата:** 2026-07-21

## Контекст

Пользователь подтвердил, что кастомная CMS будет разрабатываться в рамках этого же проекта (не отдельный репозиторий), но явно вне скоупа MVP. На момент бутстрапа инфраструктуры архитектура CMS не спроектирована.

## Проблема

Нужно решить, как MVP-решения (в частности, Content Collections, ADR 0003) не должны создавать структуру, несовместимую с будущей CMS — не проектируя саму CMS заранее, что было бы преждевременной работой без достаточных вводных.

## Варианты

1. **Спроектировать архитектуру CMS сейчас**, вместе с остальной инфраструктурой. Отклонено — недостаточно вводных (нет требований к UI администрирования, ролям, объёму контента), риск спроектировать не то, что понадобится на самом деле.
2. **Не думать про CMS вообще на этапе MVP.** Риск: структура контента MVP (Content Collections) может оказаться несовместимой с будущей CMS, что потребует болезненной миграции.
3. **Зафиксировать направление и ограничения-требования, не проектируя саму архитектуру.** Дает MVP чёткие рамки (не создавать несовместимых структур), не требуя решений, для которых пока нет вводных.

## Принятое решение

Вариант 3. CMS — подтверждённое будущее направление проекта, но её архитектура сознательно не проектируется на этом этапе. Зафиксированы только требования к будущей архитектуре:

- Совместимость с Content Collections (ADR 0003) как источником контента — CMS должна либо писать в ту же файловую Markdown+frontmatter схему, либо мигрировать её без потери структуры.
- Поддержка двуязычности (EN/RU) на уровне модели данных, а не как надстройка поверх одноязычной системы.
- Возможность self-hosted размещения — согласуется с общим направлением проекта (собственная инфраструктура, а не завязка на сторонний SaaS).

## Последствия

- Решение об архитектуре CMS откладывается до отдельной сессии/задачи с собственным discovery-интервью (требования к ролям пользователей, объёму контента, необходимости UI для незнакомых с git соавторов и т.д.).
- Этот ADR должен быть переоткрыт (не отредактирован, а заменён новым ADR со ссылкой на этот) в момент, когда пользователь решит приступить к проектированию CMS.
