# Project Analysis — anltx

Статус: **согласовано**. Документ фиксирует результат архитектурного интервью (Stage 1), обнаруженные при подключении к репозиторию факты и итоговые решения перед Stage 3.

---

## 1. Понимание проекта

**anltx** (домен anltx.xyz) — продающая контентная платформа для монетизации экспертности в аналитике. Модель — freemium: бесплатный контент (блог, раздел полезностей) наращивает авторитет и трафик, который конвертируется в платные консультации и внедрение аналитики.

- **ЦА:** начинающие веб-, дата-, системные аналитики и дата-инженеры.
- **Объект продажи:** не данные и не курсы, а экспертность и опыт — то, что нельзя получить бесплатно в другом месте.
- **MVP:** посадочная страница (`index.html`) с информацией об экспертизе/услугах + структура для блога и раздела полезностей.
- **Дальше:** наполнение контентом, собственная CMS, встроенная аналитика продукта, рост в полноценную аналитическую платформу.

Это не SaaS и не web-app в классическом смысле — на горизонте MVP/Beta это **контент-маркетинговый сайт с лидогенерацией**. Инфраструктура должна быть спроектирована под эту реальность, а не под шаблон "обычного" приложения — отсюда состав Skills/Hooks/Subagents будет смещён в сторону контента, SEO, i18n и качества сборки, а не бэкенд-разработки.

## 2. Архитектура (принятые решения)

## 3. Риски и технический долг

### 3.1 Критично — существующий репозиторий (решить до Stage 3)
На GitHub уже живёт dummy-страница с настроенным доменом и DNS. Локальная директория — не git-репозиторий. Если создать новый репозиторий с нуля вместо клонирования существующего, есть риск:
- потерять CNAME-файл и/или настройки Pages (custom domain, HTTPS enforcement);
- расхождение истории при последующем push (force-push потребуется, что опасно для настроенного Pages-деплоя).

**Рекомендация:** склонировать существующий репозиторий локально и строить инфраструктуру поверх него, а не поднимать новый `git init`.
**Нужно от тебя:** ссылка на репозиторий (или подтверждение, что можно начать с нуля и переопределить домен вручную).

### 3.2 Конфликт решений — способ авторства блога до CMS
Ты выбрал Astro отчасти для устранения дублирования (шапка/футер/меню повторяются в каждом файле × 2 локали), но при этом решил, что статьи блога до готовности CMS будут вёрстаться как отдельные страницы вручную. Это возвращает часть той же проблемы дублирования именно там, где она болезненнее всего — в блоге, у которого страниц будет больше всего.

**Альтернатива:** использовать Astro Content Collections — статьи как Markdown-файлы с фронтматтером (заголовок, дата, локаль, теги), а вёрстка (layout) переиспользуется одним шаблоном. Это не CMS и не усложняет инфраструктуру — это встроенная в Astro функция, требует только один layout-компонент на тип контента.

**Плюсы:** ноль дублирования разметки, статьи пишутся почти как обычный текст, схема данных (фронтматтер) естественным образом становится контрактом для будущей CMS — миграция на CMS упростится, а не потребует переписывания.
**Минусы:** нужно один раз спроектировать layout и схему фронтматтера — не бесплатно, но это разовые затраты на старте, а не на каждую статью.

**Рекомендация:** принять Markdown + Content Collections для блога и раздела полезностей. Лендинг (`index.html`-эквивалент) остаётся обычной Astro-страницей/компонентами, т.к. он один и не тиражируется.
**Нужно от тебя:** подтверждение или отказ (если отказ — фиксируем дублирование как осознанный технический долг).

### 3.3 Лидогенерация через serverless + Telegram
GitHub Pages отдаёт только статику — сама функция обработки формы должна жить на стороннем serverless-провайдере (например, Cloudflare Workers, бесплатный тариф, не требует полноценного хостинга — согласуется с "хостинг заведём, когда пойдут продажи"). Это первая внешняя зависимость и первый секрет в проекте (токен Telegram-бота).

**Риск:** секрет обязан жить в GitHub Actions/Cloudflare secrets, никогда в репозитории. Это прямая причина, почему в hooks нужна обязательная secrets-проверка (уже запрошена тобой).
**Рекомендация:** Cloudflare Workers как провайдер функции (бесплатный тариф, нативная интеграция с доменами, не конфликтует с GH Pages для статики). Оформить отдельным ADR перед реализацией.

### 3.4 SEO отложен, но техническая база — почти бесплатна сейчас
Ты решил заняться SEO позже. Разделяю "SEO-стратегию" (контентную) и "техническую базу" (sitemap.xml, robots.txt, канонические URL, базовые OG/meta-теги, hreflang для EN/RU). Вторая часть — это готовые Astro-интеграции (`@astrojs/sitemap`), почти нулевая стоимость внедрения сейчас и очень дорогая, если добавлять постфактум на сотнях страниц.

**Рекомендация:** включить техническую SEO-базу в MVP-скоуп (это инфраструктура, не контент-стратегия), контентное SEO — по плану, позже.

### 3.5 CMS без архитектуры — управляемый риск
Кастомная CMS официально в скоупе проекта, но не MVP, и архитектура не определена. Это нормально для текущего этапа при условии, что MVP не создаёт структур, несовместимых с будущей CMS. Content Collections (см. 3.2) снижают этот риск: файловая Markdown-модель — стандартный источник данных, на который потом легко "сажается" CMS (git-based или headless).

**Рекомендация:** зафиксировать ADR "CMS — направление, не решение" с явным перечнем требований к будущей архитектуре (двуязычность, совместимость с Content Collections, возможность self-hosted), не проектируя её сейчас.

## 4. Масштабируемость

Текущая архитектура (статика + CDN GitHub Pages) выдерживает рост трафика блога и лендинга практически без изменений вплоть до стадии, когда потребуется:
- аутентификация для клиентов (платная часть платформы);
- динамические данные (личный кабинет, дашборды аналитики как продукт);
- полноценная CMS с бэкендом.

Это естественная точка перехода на "настоящий" хостинг — совпадает с твоим планом "когда пойдут продажи, заведём хостинг". Рекомендую зафиксировать это как явную границу между фазами **MVP/Beta** (статика) и **Production/Scaling** (нужен бэкенд) в roadmap, чтобы решение не откладывалось стихийно.

## 5. Ограничения текущего решения

- GitHub Pages не поддерживает server-side логику — весь динамический функционал (формы, будущий личный кабинет) обязан жить вне GH Pages.
- Отсутствие команды сейчас означает, что процессы (review, DoD, conventions) должны быть достаточными для соло-разработки, но не создавать позже "долг ревью", когда придёт команда — правила пишем сразу пригодными для роста, без лишней бюрократии сейчас.
- Ручное решение по контенту (3.2) и forms-провайдеру (3.3) требуют подтверждения перед тем, как Stage 3 зафиксирует структуру директорий.

## 7. Обнаруженные при подключении к репозиторию факты (важное расхождение с интервью)

При клонировании `github.com/bogdanvrublevsky/anltx.xyz` выяснилось, что это **монорепозиторий**, а не изолированный проект под сайт:

```
main (ветка) содержит:
  main/    — текущая dummy-страница anltx.xyz (index.html, styles.css, favicon.svg) — ОБСУЖДАЛОСЬ В ИНТЕРВЬЮ
  dlext/   — Chromium-расширение "data layer inspector" (dlext.anltx.xyz по README)
  ttapp/   — helper для настольных RPG, с собственным auth (ttapp.anltx.xyz по README)
  sgame/   — веб-игра (sgame.anltx.xyz по README, только README, кода нет)
  treev/   — визуализация деревьев (treev.anltx.xyz по README, только README, кода нет)
```

`README.md` репозитория описывает более широкое видение, не раскрытое в интервью: `lwtms.anltx.xyz` (light-weight tag management system) и `sstms.anltx.xyz` (server-side TMS) — судя по всему, это и есть конкретное содержание "полноценной аналитической платформы" из ответа про дальнейшее развитие продукта. Кода для lwtms/sstms в репозитории пока нет — только упоминание в README.

`deploy.yml` на данный момент публикует на GitHub Pages (`gh-pages`, custom domain `anltx.xyz`) только `main/` и `ttapp/`.

**Решение по скоупу (утверждено):** текущий бутстрап инфраструктуры (CLAUDE.md, memory, ADR, skills, hooks, subagents) охватывает **только `main/`** — сайт, обсуждённый в интервью. `dlext`, `ttapp`, `sgame`, `treev`, `lwtms`, `sstms` — вне скоупа, зафиксированы как отдельные будущие направления в roadmap (Stage 12), инфраструктура под них не проектируется до отдельного запроса.

### 7.1 Инцидент безопасности (устранён)
В `ttapp/data/users.json` был обнаружен пароль администратора в открытом виде (`admin1234`), закоммиченный в **публичный** репозиторий, из которого собирается публичный GitHub Pages сайт. `ttapp/auth.js` сравнивал пароль как plaintext.

**Действие:** значение пароля заменено на плейсхолдер `ROTATED_SET_VIA_ENV_BEFORE_USE` в HEAD ветки `main`, закоммичено и запушено (`29e32e3`). Redeploy `gh-pages` подхватит исправление автоматически при следующем срабатывании `deploy.yml`.

**Остаточный риск:** старый пароль остаётся в истории git (коммит `88009e6` и ранее) — полная зачистка истории (`git filter-repo`/BFG) не выполнялась, так как требует force-push и отдельного подтверждения (деструктивная операция). Если пароль `admin1234` использовался где-либо ещё — рекомендуется сменить его там. Проработка нормальной модели секретов для `ttapp` — вне скоупа (проект вне текущего фокуса).
