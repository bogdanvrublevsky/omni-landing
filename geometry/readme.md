# Техническая спецификация: Генератор планет (hex/pentagon sphere)

## 1. Суть проекта

Библиотека для процедурной генерации и рендера сферических "планет", собранных из шестиугольных и пятиугольных ячеек — для использования в стратегической игре (в разработке у автора), где размер игровой карты-планеты варьируется от партии к партии.

Веб-страница из двух зон:
- **слева (`aside`)** — единственный контрол: размер планеты (`frequency`);
- **справа** — 3D-визуализация Three.js.

Это dev/preview-инструмент поверх библиотеки `geom.lib.js`, а не сама игра — сама игра будет импортировать библиотеку отдельно.

## 2. Зафиксированные решения (важно, не переоткрывать без явной причины)

| Вопрос | Решение |
|---|---|
| Топология ячеек | Многогранник Голдберга (Goldberg polyhedron) GP(f,0): икосаэдр → геодезическое подразбиение с параметром `frequency` (f) → двойственный многогранник |
| Число пятиугольников | Всегда ровно **12**, при любом f — это не выбор, а следствие формулы Эйлера для трёхвалентных многогранников из пятиугольников и шестиугольников (V−E+F=2 ⟹ p=12 независимо от числа шестиугольников h). Строго доказано, пересчитывать/оспаривать нет смысла |
| Число граней (n) | n = 10f² + 2 (12 пятиугольных + (10f²−10) шестиугольных). f — единственный параметр "размера" |
| Правильность граней | **Не** строго правильные многоугольники (в отличие от первой версии проекта, см. раздел "История"). Грани приближённо правильные, при f>1 не идеально плоские — это неизбежное следствие того, что у структуры недостаточно симметрии, чтобы совместить плоскостность + правильность + равносторонность одновременно (тот же эффект, что у крупных фуллеренов C70+) |
| Источник геометрии | Вычисляется алгоритмически в момент вызова, **без** внешнего датасета/npm-пакета — ни в рантайме, ни на dev-этапе |
| Стек рендеринга | Three.js через CDN (unpkg, importmap в `index.html` `<head>`), без npm/бандлера. Требует сети — офлайн-работа сознательно принесена в жертву тому, чтобы не хранить копию модуля в репозитории |

## 3. Алгоритм (`geom.lib.js`)

1. **`icosahedronBase()`** — 12 вершин, 20 треугольных граней правильного икосаэдра (координаты через золотое сечение φ), нормализовано на единичную сферу. Грани идут в порядке, дающем нормаль наружу.
2. **`subdivideIcosahedron(frequency)`** — каждая из 20 граней делится на f² маленьких треугольников по барицентрической сетке (Class I Goldberg–Coxeter subdivision), точки проецируются на сферу (`normalize`). Вершины на общих рёбрах соседних граней дедуплицируются по округлённым координатам (6 знаков), чтобы не плодить дубликаты на стыках.
3. **`buildDual({ vertex, face })`** — для каждой вершины триангулированной сферы строится грань двойственного многогранника: обходим все инцидентные треугольники в циклическом порядке (по цепочке `incoming → outgoing`, восстановленной из соседних рёбер) и берём их центроиды (спроецированные на сферу) как вершины новой грани. Вершины, унаследованные от икосаэдра (12 штук, degree 5) → пятиугольники; все остальные (degree 6, появившиеся при подразбиении) → шестиугольники.
4. **`generatePlanet(frequency)`** — обёртка над (2)+(3), возвращает `{ name, vertex, face }`, совместимый с существующим рендер-пайплайном (`facesToFillGeometry`/`facesToEdgeGeometry`, fan-триангуляция от первой вершины грани).

Валидировано вычислительно (вне репозитория, разовым скриптом при разработке): для f = 1, 2, 3, 4, 8 совпадают n = 10f²+2, V = 20f², формула Эйлера V−E+F=2, гистограмма граней даёт ровно 12 пятиугольников, все нормали граней смотрят наружу, вырожденных граней нет. f=1 отдельно проверен как вырожденный случай — даёт ровно додекаэдр (12 пятиугольников, 0 шестиугольников), что совпадает с независимо известной математикой (дуал икосаэдра = додекаэдр).

## 4. Компонентная архитектура

```
geometry/
  geom.lib.js   — чистая библиотека: генератор (icosahedronBase/subdivideIcosahedron/
                  buildDual/generatePlanet) + exportPlanet/importPlanet. Ноль
                  зависимостей (никакого THREE, никакого DOM) — рассчитана на импорт
                  из любого проекта (игры), не только из этой demo-страницы.
                  Публичный контракт задокументирован JSDoc-аннотациями
                  (@typedef Planet/PlanetFile, @param/@returns/@throws на
                  generatePlanet/exportPlanet/importPlanet) — IDE подхватывает их
                  без билд-шага. generatePlanet валидирует frequency (целое >= 1).
  render.js     — весь Three.js и вся связка с DOM для этой demo-страницы:
                  createViewer (сцена/камера/свет/OrbitControls/showBody) +
                  обработчики UI (слайдер frequency, скачать/загрузить). Импортирует
                  geom.lib.js, но не наоборот — geom.lib.js ничего не знает про
                  render.js. Разделение библиотека/клиент явное: рендер — не часть
                  библиотеки.
  index.html    — чистая разметка, без единой строки JS внутри файла: aside с
                  range-контролом "frequency" и кнопками файла, <div id="viewer">,
                  <script type="importmap"> в <head> (three/three-addons →
                  unpkg.com, версия зафиксирована — three@0.166.1), и
                  <script type="module" src="./render.js"> в самом низу.
                  Нет vendor/ — Three.js больше не хранится в репозитории,
                  render.js импортирует его через bare specifier ('three' /
                  'three/addons/...'), резолвится через importmap.
  package.json  — только "type": "module" + "main"/"exports" на geom.lib.js.
                  Обязателен, не опционален: в браузере <script type="module">
                  не смотрит на package.json вообще, но Node.js для .js-файлов
                  определяет CommonJS/ESM по полю "type" в ближайшем package.json
                  (по умолчанию — CommonJS). Без этого файла geom.lib.js,
                  импортированный напрямую в Node (а не через <script>), либо падает
                  на самом `import`, либо молча резолвится как CommonJS без named
                  exports — проверено вычислительно на 4 сценариях подключения,
                  3 из 4 без этого package.json ломались. Нет ни одной npm-зависимости
                  в нём — только это одно поле, которое реально требуется рантаймом.
```

Код (идентификаторы, комментарии, JSDoc, тексты ошибок) — только на английском, независимо от языка документации/диалога.

## 5. Сохранение/загрузка (`exportPlanet`/`importPlanet`)

`generatePlanet` возвращает, помимо `vertex`/`face`, ещё `frequency` и `cells` — параллельный `face` массив, один объект на ячейку (пока пустой `{}`), точка расширения под будущие игровые свойства ячейки. Индекс в `cells`/`face` — стабильный ID ячейки, т.к. генерация детерминирована (один и тот же `frequency` всегда даёт ячейки в одном порядке).

Файл сохранения — **полный снапшот** (`{ format: "anltx-planet", version, frequency, vertex, face, cells }`), не только `frequency`. Так сохранённая планета не зависит от будущих правок алгоритма генерации (например, relaxation-шага или смены Class I на Class II/III подразбиение, см. ниже) — при загрузке геометрия не пересчитывается заново, а берётся из файла как есть, поэтому не может разойтись с тем, что видел игрок на момент сохранения.

## 6. Не забыть при развитии

- Грани не идеально плоские при больших f — сейчас рендерятся fan-триангуляцией от первой вершины, нормали считаются через `computeVertexNormals()`. Визуально на глаз не заметно (проверено до f=20), но если понадобится физическая точность (коллизии, точные площади/центры ячеек для геймплея) — потребуется либо relaxation-шаг (например, Lloyd relaxation) для выравнивания граней, либо явный учёт неплоскостности в потребляющем коде.
- `frequency` в текущем UI ограничен диапазоном 1–20 (n до 4002) из соображений отзывчивости live-слайдера при пересчёте на каждое событие `input`. Сам генератор верхнего предела не имеет.
- Для игры, скорее всего, понадобится слой поверх текущего вывода: граф соседства ячеек для геймплея, материалы/раскраска по биому и т.п. (сами свойства ячейки уже есть куда положить — в `cells[i]`) — сознательно вне текущего скоупа этого dev-инструмента.
- Формат файла версионируется (`PLANET_FORMAT_VERSION`) — при несовместимом изменении структуры `cells`/`vertex`/`face` увеличить версию и решить, нужна ли миграция старых сохранений.
- Class I Goldberg–Coxeter (GP(f,0)) — не единственный вариант подразбиения; более общие Class II/III (GP(m,n), m≠n) дают другие узоры и другую (более сложную) формулу n, но не нужны, пока не появится конкретное требование со стороны игры.

## История

Первая версия этого проекта строилась вокруг каталога **именных** тел (Платоновы/Архимедовы/Джонсона/призмы/антипризмы) из датасета Hart (npm-пакет `polyhedra`), с UI выбора x (доминирующий тип грани) / n (число граней) / конкретное тело, и требованием строгой правильности всех граней. Модель давала только фиксированный конечный список тел на комбинацию (x, n) и не позволяла запросить произвольный "размер" — для планет стратегической игры это оказалось непригодно (для x=6, например, во всём датасете нашлось ровно 3 тела: n=8/14/32, и большего числа математически не существует при требовании строгой правильности граней). Заменена на параметризуемый генератор многогранников Голдберга, описанный выше.
